## 二、「模型」原来是个自由文本框

改动前，训练表单里的模型是：

```html
<input v-model="form.model" class="field__control" />
```

默认值 `yolo11n.pt`。用户得自己记得 `yolo11s.pt` 的拼写，写错了要等训练子进程
起来报「找不到权重」才知道。更糟的是本机**根本没有 `yolo11n.pt`**——
`.runtime/ultralytics/weights/` 里只有 `yolo11m.pt` / `yolo11s.pt` / `yolo26n.pt`，
而 n 既是表单默认值、又是现役最好归档（0.7675）的基座。

### 清单放在引擎侧，不放在路由里

新增 `fire_sight_platform/training/catalog.py`，而不是把清单写在 `routers/train.py`：

> 让「显存守卫」与「界面」共用同一份真相，避免「下拉里能选、一点就 400」。

清单六个规模全列（用户批准「六个都列」），本机没有的 `present=False`，
界面标「需下载」并说明选中会联网抓权重——**列出可选项比藏起来好**：
真实失败会给出一次明确的报错（找不到权重会真的联网抓），而不是让下拉里凭空少几项、
用户以为是 bug。

**默认值改成第一个本机已有的**（即 `yolo11s.pt`），不写死 `yolo11n.pt`。
理由：默认值不该让用户一点就触发一次网络下载。

`list_options()` 只读文件系统，不联网、不 `import torch`——重量级导入留在训练侧。

## 三、删除：移进回收目录，而不是抹掉

用户选的是「移到回收目录，可恢复」，并且要「删除时让我勾选」——
即每次删除给一个复选框，**不把「归档」与「训练现场」绑死**。
有的现场值得留着（比如想回看曲线），但权重想清掉；反过来也有。

### 落脚点

`common/paths.py` 新增：

```python
# 「删除」归档与训练现场时的落脚点：**移进来，不是抹掉**。
# 权重是几十分钟到两小时的产物，误点一下就永久消失的代价太大。移进这里之后
# 页面上不再出现、磁盘不立即释放，代价换来的是「删错了能捞回来」。
# 想真正释放空间，由用户手工清空这个目录——这个决定故意不自动化。
TRASH_DIR: Path = MODELS_DIR / ".trash"
```

**「不自动化清理」是个刻意的决定**，不是没做完：自动过期清理意味着「删了之后
过一阵它自己没了」，用户无法预知。宁可让磁盘占着，让用户自己决定什么时候真正放手。

### 三条不留假成功的规矩

1. 只有训练现场、没有归档权重时，**不勾选**返回 **400** 并说明：
   「只有训练现场、没有归档权重；如需删除请勾选『同时删除训练现场』」。
   不能返回 `removed_archive=False, removed_run=False` 的「成功」——
   那看起来像删掉了。
2. 一件都没搬走时，把空回收目录 `rmdir` 掉，否则回收站堆空壳、看不出删过什么。
3. 同一秒删两次会撞目录名，所以 `_unique_dir()` 撞了就加 `-2`、`-3`。

### 删完必须清推理缓存

`models.py` 的删除路径里显式调 `deps.clear_infer_cache()`。
不调的话识别页还拿着内存里那份**已经不存在的模型**在推理，页面上一切正常——
又一个「看起来正常但结果不对」。

## 四、真缺陷：清空壳的边界取自两个不一致的来源

`recycle()` 删掉嵌套布局（`trained/<run_id>/<exp>/best.pt`）里的 `<exp>/` 之后，
要把外层的 `<run_id>/` 空壳一起清掉。测试
`test_delete_nested_archive_cleans_the_empty_shell` 一直失败：外层空壳留着。

根因是两个参数的**来源不同**：

| 参数 | 来源 | 是否跟随 monkeypatch |
|---|---|---|
| `archive_root` | `deps.archived_runs()` 返回 | ✅ 落在 tmp_path |
| `stop`(= `TRAINED_MODELS_DIR`) | `recycle_service` 导入时绑定的模块常量 | ❌ 指向真实工作区 |

于是 `stop in current.parents` 永假，while 循环一次都不进。
**不报错，只是空壳悄悄清不掉。**

### 我第一版修法是错的（重要）

我加了个 `archive_floor(archive_root)` 反推归档根：

```python
if (archive_root / "best.pt").exists():
    return archive_root.parent
if (archive_root.parent / "best.pt").exists():
    return archive_root.parent.parent
```

**嵌套布局里 `<exp>/` 自己就装着 `best.pt`**，所以两个分支给出同一个答案；
`stop` 变成 `archive_root.parent`，恰好等于起始节点，循环照样不进。
**改了代码，行为一点没变。** 测试仍失败——这是唯一识破它的东西。

### 最终修法：不推断，由调用方显式传入

`recycle()` 新增参数 `archive_base: Optional[Path] = None`（归档根，清空壳不许越过；
`None` 表示不清空壳），删掉 `archive_floor()`。docstring 写明
**为什么不能在本模块内靠路径形状反推**：归档有两种布局，嵌套布局里 `<exp>/`
自己也有 `best.pt`，看自己有没有 best.pt 区分不出浅层与嵌套。

调用方给出：

```python
removed = recycle(
    run_id=req.run_id,
    archive_root=run.root if run is not None else None,
    run_root=run_site.root if (req.with_run and run_site is not None) else None,
    # 归档根由这里给出（本模块的 deps 侧最清楚它指向哪）；清空壳时不许越过它
    archive_base=deps.TRAINED_MODELS_DIR,
)
```

副作用（好事）：`recycle_service` 不再依赖自己导入时那一份 `TRAINED_MODELS_DIR`，
改用调用方实际使用的根目录，**消掉了那个静默失效的耦合**。

## 五、数据集换代：为什么这次要破「raw 只读」

本项目一直有一条约定：**raw 只读，只有 `processed/` 下的数据用于训练**。
这一版故意破掉它。

先看清楚新旧两份数据是什么关系。实测：

| | 旧 `data/processed/D-Fire/train` | 新 `data/raw/D-Fire` |
|---|---|---|
| train | 13776 | 14122 |
| val | 1722 | 3099 |
| test | 1723 | 4306 |
| 合计 | 17221 | 21527 |

**新 ∩ 旧 = 17221 = 旧的全部；新独有 4306 = 新的 test。**
也就是说：**新 train + 新 val = 旧全部**（同一批图被重新切了一遍），
新 test 是纯新增（数目与官方 test 集 4306 一致，此前从未处理过）。

### 判据不是「新旧」，是「可不可再生」

- processed 下的切分是**本项目**按 8:1:1 随机分的（seed 42、无分层无分组），
  随时可以重跑出来；
- 这一份是**提供方给的**，切分本身就是要保住的资产。

再复制一份进 processed 会暗示「它可重建」——那是错的。
所以 `data/raw/D-Fire/data.yaml` 直接就位，`fire_sight_meta` 记
`split_strategy: provided` / `regenerable: false`。

文件头写了一段注释说明这件事，因为下一个人看到「raw 里有 data.yaml」
第一反应会是「这违反了约定」。

### 代码侧三处同一个特例

| 文件 | 位置 | 做的事 |
|---|---|---|
| `training/service.py` | `_resolve_dataset_yaml()` | `dataset == "D-Fire/raw"` → 直接给 raw 的 yaml |
| `routers/infer.py` | `_dataset_dirs()` | 返回 `List[Tuple[str, Path]]`，raw 那条**排最前** |
| `evaluation/service.py` | `_resolve_yaml()` | 同样的特例（评估也要能落在新数据上） |

`_source_options()` 要认**两种相反的布局**：processed 是 `<ds>/images/<split>`，
raw 是 `<ds>/<split>/images`。内层循环加 `break`，避免两种布局都命中时出重复行。

### 标签解析要跟着改

`_dataset_label()` 原来只按 `PROCESSED_DATA_DIR` 反算相对路径。
`D-Fire/raw` 不在 processed 下，只按它算会**退化成目录名 `D-Fire`**——
训练记录里就看不出这一份到底是哪个。改成两个 base 依次试。

验证往返闭合：

```
D-Fire/raw    -> data/raw/D-Fire/data.yaml              label = D-Fire/raw
D-Fire/train  -> data/processed/D-Fire/train/data.yaml  label = D-Fire/train
demo_fire     -> data/processed/demo_fire/data.yaml     label = demo_fire
```

## 六、旧归档为什么要标「不可比」

既然是**同一批图重新切**的，那么新 val 里必然有一部分图当初进过旧 train。
**旧归档在新 val 上评估会虚高。**

所以旧归档整个标记为「旧数据不可比」（`ModelInfo.legacy`），
不是「标记一下继续用」。两边不在同一条起跑线上，拿它们的数去挑模型是错的。

### 判据用数据集标签，不是时间、也不是 run_id 形状

```python
def _is_legacy(dataset: Any) -> bool:
    """判据是数据集标签，不是时间：`D-Fire/train` 算旧，`D-Fire/raw` 算新。
    用时间判断会在「回滚到旧数据重训」时标错。
    标签缺失时按旧处理——目前只有旧归档可能缺标签。"""
    return str(dataset or "") != "D-Fire/raw"
```

两条容易被后人写坏的替代方案，都补了回归测试：

- **按时间**：回滚到旧数据重训时，新产物会被标成「新」，而它其实是旧的。
- **按 run_id 字符串匹配**：早期布局的 run_id 自带斜杠
  （`20260926-190635-D-Fire/train-yolo11n`），名字里带 `D-Fire/train`。
  测试造了 `20260105-D-Fire/train-yolo11n`（标签说它用旧的）与
  `20260106-D-Fire-raw-n`（标签说它用新数据），断言**名字带 train 的 legacy=True、
  名字带 raw 的 legacy=False**——这个测试就是为了防止判据退化成字符串匹配。

「标签缺失按旧处理」是**宁可多标一个，也不要漏标一个让数虚高**。

### 顺带：旧数据的泄漏此前已经量过

- dHash 最小汉明距离：**≤0 占 21.1%**（363 张）、≤4 占 46.4%、≤8 占 56.7%；
  对照 train 内部随机两两均值 30.5、中位 31。
- 排除过两种虚高可能：逐字节重复（跨 split 重复 0 组、同名 stem 0 个）与
  指纹退化（13776 张 → 11556 个不同指纹）。
- 已用图证实：`val/AoF00554.jpg`（Camera0001，12 Aug 2020 **08:14:35**）↔
  `train/AoF00553.jpg`（同机位 **08:14:25**）＝相隔 **10 秒**；
  `val/AoF04480.jpg`（17 Oct 2019 **19:36:00**）↔ `train/AoF04084.jpg`（**19:36:13**）
  ＝相隔 **13 秒**。两对画面肉眼不可区分。

新数据大概率仍有同类重叠（它的 train/val 也是从官方 train 里划的），
**用户明确决定不量、直接开训**。

## 七、评估划分：val 选模型，test 留给最终汇报

用户决定：对比评估可选 `val` 或 `test`，**默认 val**；平时用 val 选模型，
最终汇报时用 test 出一组数（test 从未参与任何决策）。

`train` **故意不在可选列表里**——在训过的数据上报指标没有意义，只会误导。

`split` 一路透传到 `ValConfig.split` → `model.val(split=...)`。
注意**没有**为 test 另建一份 yaml：那会让「哪个划分」有两个真相。

### 真缺陷：`or` 把空串悄悄兜成了合法值

最初写的是：

```python
split = (req.split or "val").strip().lower()
```

空串走 `or` 变成 `"val"`，于是 `POST {"split": ""}` 返回 **201 创建成功**而不是 400。

**修法是去掉 `or`**：

```python
# 空串**不**兜成默认值：不传字段（Pydantic 给 "val"）和显式传了空串
# 是两件事，后者说明调用方算错了划分名。悄悄兜底会让这类错永远看不见。
split = req.split.strip().lower()
```

这个 bug 的代价比看上去大：它真的**启动了一个任务并占住了 GPU 锁**，
导致后面 5 个用例的 POST 全被 409 挡掉、`.json()` 里没有 `id`，
连带报出 7 failed。**这批失败里 5 个是级联的，只有 1 个是真病。**

> 教训：批量失败里有 `KeyError: 'x'` 且单跑通过时，先查前一个用例是不是
> 留了全局状态（锁/单例），别去改后面那几个测试。

### 顺带修掉：图件互相覆盖

`evaluate_weights` 用 `Path(weights).stem` 当输出目录名，而归档权重**都叫
`best.pt`** → 两个模型、两个划分全落到同一目录，留下的是后跑的那份、
文件名却写着前一个。改为 `f"{stem}-{split}"`。
（这是上一版 devlog 第「遗留」一节里记着的那条。）

## 九、踩到的坑

### 运行中的服务不会自动加载新代码，E2E 新用例会被静默 skip

E2E 新加的「旧数据归档带标记」用例第一次跑**被跳过**了。查明：
8000 上的服务还是旧代码，`GET /api/models` 响应里**根本没有 `legacy` 键**。

**跳过和通过看起来一样绿，含义完全不同。** 定位方法：`Get-NetTCPConnection`
拿监听 PID，再沿 `Get-CimInstance Win32_Process` 的 `ParentProcessId` 往上追到
`cmd.exe /c "...python.exe -m fire_sight.cli ... > .runtime\logs\serve-<时间戳>.log"`
——日志名带时间戳 + 路径指向本仓库 ⇒ 是我自己起的服务，可安全收。
重启后 `legacy` 出现，用例转绿。

### 编辑工具把换行吃掉了

改 `routers/eval.py` 时 `old_string` 边界没贴紧，把
`dataset = _resolve_dataset(...)` 与 `try:` 之间的换行吃掉，
拼成一行 `dataset = _resolve_dataset(req.run_ids, req.dataset)    try:` → 语法错误。

**改完 Python 文件先用 `python -c "import ast; ast.parse(open(...).read())"`
验语法，比跑测试快。**

### PowerShell 里 `python -c` 的 f-string 嵌套引号会炸

```
.\.venv\Scripts\python.exe -c "print(f'{\"a\"}')"   # 报 '{' was never closed
```
改用 `write` 工具落一个脚本文件再跑。

### `Invoke-RestMethod ... .Count` 在字符串插值里行为不一致

本 session 被它骗了三次（一次把 9 条训练记录报成 1 条）。
改用 `(Invoke-WebRequest).Content | ConvertFrom-Json`。
