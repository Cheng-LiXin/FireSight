## 一、显存守卫原来没有模型规模项

### 问题怎么发现的

上一轮（v1.3.2）加显存守卫时，预算模型是 `batch × imgsz²`，常数标定在 yolo11n 上。
我在交付说明里就写了这句：

> 守卫的常数是在 yolo11n 上标定的，只看 `batch × imgsz²`，**不含模型规模项**。
> 换 yolo11s/m 时真实需求更高，守卫可能放行一个会 OOM 的 batch。

而 P0-1 探针的结论是「分辨率杠杆到头了，下一站转模型容量」——**换大模型这件事被卡在
这个缺口上**。所以先补它。

### 不拍常数，去测

这个项目里已经有过「拍一个听起来合理的常数」的教训（配色校验器丢失、误判管道死锁），
所以先看能不能实测。检查后确认：GitHub 可达，`yolo11s.pt`（18.4 MB）与 `yolo11m.pt`
（38.8 MB）都能下。**那就实测。**

方法：峰值显存 ≈ **模型固有开销**（权重/梯度/优化器状态）+ **激活开销**（∝ batch × imgsz²）。
对每个模型跑**两个 batch 点**做线性拟合，取**斜率之比**作为因子——斜率才是纯激活开销，
常数项会污染比值。

测量口径尽量贴近真实训练：不传 `amp`（让 ultralytics 用默认 AMP）、不传 `optimizer`、
`cache=False`、`workers=0`（排除 DataLoader 干扰），设备是真 GPU。

### 结果

| 模型 | batch=4 | batch=8 | batch=16 | batch=32 |
|---|---|---|---|---|
| yolo11n | — | 672.4 | — | 2235.8 |
| yolo11s | — | 1202.7 | — | 4041.4 |
| yolo11m | 1361.1 | (2367.3) | 4347.9 | (8186.5) |
| yolo11l | 1709.9 | — | 5524.7 | — |
| yolo11x | 2772.3 | — | 8490.2 | — |

（括号里是第一次测的、后来判定不宜用于拟合的点。）

拟合出的斜率与因子：

| 模型 | 斜率 MB/batch | 因子 |
|---|---|---|
| yolo11n | 65.1 | 1.00 ← 标定 |
| yolo11s | 118.3 | 1.82 |
| yolo11m | 248.9 | 3.83 |
| yolo11l | 317.9 | 4.89 |
| yolo11x | 476.5 | 7.32 |

### 两个坑

**1. yolo11m 在 `batch=32 × imgsz=480` 就吃满了整张卡**（8186.5 MiB / 8187.5 MiB）。
这既是问题本身的证据，也让那个拟合点不可信——**饱和的点不能用**（系统已经贴到上限，
测出来的「需求」被截断）。所以重测了 m 的低 batch 点：斜率 248.9，与第一次那组算出的
242.5 只差 2.6%，说明第一次的拟合没有被严重扭曲。**但不能靠运气，饱和点一律弃用。**

**2. yolo11x 在 `batch=16` 报到 8490 MiB，超过了显存总量 8187.5 MiB。**
这不可能是真的显存占用。单位先排除了：`torch.cuda.get_device_properties().total_memory`
报 8187.5 **MiB** = 8585 MB，而守卫用的 `8188` 也是 MiB（nvidia-smi 口径），
`max_memory_allocated()/1024/1024` 同样是 MiB——**三处同口径，没有换算 bug**。

真正的解释是驱动开了**系统内存回退**（CUDA sysmem fallback）：显存不够时溢出到系统内存。
这一点对守卫很重要——**超预算不一定 OOM，而是走 PCIe 变得极慢**。OOM 至少会报错，
「能跑但慢十倍」更难察觉。已写进 `vram.py` 的已知偏差。

### 因子是否够保守

把守卫各档的上限与实测真实上限比一下（imgsz=480）：

| 模型 | 守卫上限 | 实测真实上限 | 余量 |
|---|---|---|---|
| yolo11n | 72 | ≈123 | 1.7× |
| yolo11s | 39 | ≈67 | 1.7× |
| yolo11m | 18 | ≈31 | 1.7× |
| yolo11l | 14 | ≈23 | 1.6× |
| yolo11x | 9 | ≈15 | 1.7× |

每档都低于实测值，且余量一致。这个余量不是新加的，它**继承自标定点**——标定假设那次
`batch=72 × imgsz=480` 用满了 8 GB，而实测 n 在 72×480 下只需约 4.8 GB。
我把这件事写进了注释：现在终于知道那个保守度是多少，而不是「大概偏保守」。

### 未知模型怎么办

从归档 `best.pt` 继续训练时，文件名说明不了规模，于是：

- 按 yolo11m 的因子处理（比不设限安全：不设限等于把 m 当成 n 放行，实测超预算 2.2 倍）
- **在接口和界面上标明 `model_measured=false`**，提示语写「该模型规模没有实测数据，
  上限按 yolo11m 估算——参数更多时请再留余量」

不标出来，用户会以为这个上限也实测过。**这是最坏的一种诚实缺失。**

### 防止后人改常数不重测

`MODEL_MEASUREMENTS` 里留了原始峰值数据，并有一条测试**从它重算因子**：

```python
base = slope(vram.MODEL_MEASUREMENTS["yolo11n"])
measured = slope(points) / base
assert abs(vram.MODEL_FACTORS[name] - measured) < 0.02
```

有人改了因子却不重测，这条就会挂。因子是从真实训练里量出来的，不是魔法值。

## 二、一条从没执行过的 E2E 用例

`training.spec.ts` 的门控写在**文件级 `beforeEach`** 里：

```ts
test.beforeEach(() => {
  test.skip(!process.env.FIRESIGHT_E2E_TRAIN, '需设 FIRESIGHT_E2E_TRAIN=1（会真的跑训练）')
})
```

它对整个文件生效，于是同文件里那条**不需要训练**的 409 用例也一起被跳过。
默认跑显示「2 skipped」，看起来像正常的按需跳过——**所以一直没人发现**。

改成在真训练那条用例内部 `test.skip(...)`，超时也一并下沉（`test.setTimeout`），
否则 409 用例也要背上 5 分钟的超时。

### 修完之后发现那条用例本身也没在测标题

它原来只断言 `/api/system/status` 有 `holder` / `busy` 两个字段：

```ts
expect(body.gpu_job).toHaveProperty('holder')
expect(body.gpu_job).toHaveProperty('busy')
```

标题是「已有训练在跑时，识别接口返回 409 提示占用者」，但它既没碰到 409，
也没验证任何提示。原来的注释还坦白写着「由后端用例覆盖判定逻辑」——
问题在于**它连渲染路径也没验**。

端到端里真占住 GPU 锁做不到（需要另一条真训练），所以改用**路由拦截**造出后端那个
409，验证界面把 detail 原样渲染出来：

```ts
await page.route('**/api/train/jobs', (route) =>
  route.fulfill({ status: 409, body: JSON.stringify({ detail: 'GPU 正被「train」占用' }) }))
```

判定逻辑仍由后端 `test_17` / `test_20` 覆盖，分工是清楚的。

> 顺带确认了一件事：我原以为 409 的 detail 是裸的 `"train"`（那样界面就会显示
> 一个词）。实际上 `deps.GpuBusy.__init__` 已经把它格式化成「GPU 正被「train」占用」，
> 所以不用改后端文案。

## 三、我这轮犯的错

### 3.1 手动验证时真起了一次训练

验证「同一组 batch/imgsz 在 n 上放行、在 m 上被拒」时，我对 `/api/train/jobs` 发了
两个 POST。写测试时我特意只走拒绝分支（避免起进程），**手动验证时却忘了**——
`yolo11n` 那条返回 201，真的在 GPU 上起了一次训练。

发现后立刻停掉（状态 `stopped`，GPU 锁正常释放），删掉了现场目录
`runs/training/20260927-155049-demo_fire-yolo11n`，确认 `models/trained` 仍只有正确的
2 个归档、没有多出产物。

意外收获：这次真实执行顺带验证了 v1.3.2 的停止状态机（`stopping` → `stopped`，
锁释放）。但**这是运气，不是方法**——放行那一侧本来就该在单测里覆盖。

### 3.2 截图脚本取错了输入框序号

`.launcher input` 的 `nth(1)` 是「轮数」而不是「模型」（第一个 input 才是模型），
往数字框里填 `yolo11m.pt` 自然失败。改用 `getByLabel('模型')`。
**这个项目里定位元素一直用标签，我不该退回序号。**
