# 2026-09-27 · 运行时目录收敛与训练显存守卫

> 版本：v1.3.2 · 触发：用户报告「点开始训练后 C 盘被极速挤占」
> 相关代码：`fire_sight_platform/common/runtime_env.py`、`training/vram.py`

---

## 起因

用户报：点训练中心的「开始训练」之后，C 盘空间被极速吃掉，资源管理器爆红。

第一反应是训练在往系统盘写。但训练显式传了
`project=E:\FireSight\runs\training`，按设计应该全落在 E 盘。所以先把「到底
写了什么」量出来，再谈改哪里。

## 但顺着查下去，项目确实在漏

真正有价值的是这条线索查出来的东西。追到 ultralytics 8.4.163 的配置解析，
根因在 C 盘上一份**机器级**的全局配置：

```jsonc
// C:\Users\19832\AppData\Roaming\Ultralytics\settings.json
"datasets_dir": "C:\\Users\\datasets",
"weights_dir":  "C:\\Users\\19832\\weights",
"runs_dir":     "C:\\Users\\19832\\runs",
```

`ultralytics.utils` 在 **import 时**就把这三个值读成模块常量
（`RUNS_DIR`/`WEIGHTS_DIR`/`DATASETS_DIR`），此后 `SETTINGS.update()` 只能改动
「读字典」的那部分调用，改不动常量。于是任何**没显式传 `project`** 的调用都
会落到这份配置指向的路径上。实测到的漏点：

1. **`evaluate_weights()` 的 `model.val()` 没传 `project`**
   → 写出 `C:\Users\19832\runs\detect\val`、`val-2`，共 24 个文件 2.4 MB
   （`ultralytics/cfg/__init__.py:550` 的 `get_save_dir()` 回退到
   `SETTINGS["runs_dir"]`）
2. **AMP 自检**用 `WEIGHTS_DIR / "yolo26n.pt"`（`utils/checks.py:1020`）
   → `C:\Users\19832\weights\yolo26n.pt` 5.3 MB
3. **训练任务配置**走 `tempfile.gettempdir()` → C 盘 Temp
4. **matplotlib 字体缓存**（ultralytics 画图要用）→ `%LOCALAPPDATA%`
5. `Arial.ttf` 755 KB → `%APPDATA%\Ultralytics\Arial.ttf`

单看每一条都不大，但都属于「不该写系统盘」的那一类，而且第 1 条已经实际发生。

## 改法

### 改道靠环境变量，必须抢在 import 之前

```python
apply_runtime_env()          # 设 YOLO_CONFIG_DIR / TEMP / MPLCONFIGDIR / TORCH_HOME …
from ultralytics import YOLO # 它在这行才读 settings.json
pin_ultralytics_paths()      # 再把三处目录钉进运行时目录下那份 settings.json
```

两步都要：本进程内 `get_save_dir()` 读的是 `SETTINGS` 字典，`update()` 立刻
生效；后续进程靠落盘的 `settings.json`。少了任一步都会漏。

### 拒绝改写用户的全局配置

`pin_ultralytics_paths()` 会检查 `ultralytics.utils.USER_CONFIG_DIR` 是否在
运行时目录下。**不在就拒绝写入并告警**——那说明改道晚了一步，此时正确做法是
让改道生效，而不是顺手把人家机器级的设置改掉。

### 落点

```
.runtime/
  tmp/           任务配置、子进程 TEMP、torch 编译缓存
  ultralytics/   YOLO_CONFIG_DIR（内含钉定过的 settings.json）
  cache/         matplotlib 字体缓存、TORCH_HOME、HF_HOME
  evaluation/    fs-val 的评估图件
```

评估图件是过程副产物、没有消费方，所以丢进 `evaluation/` 而不是 `runs/`。

## 顺带修掉的显存问题

查 `args.yaml` 时看见了那次训练的真实配置：

```
epochs=10  batch=48  imgsz=640  device=0  fraction=1.0
```

前端默认是 `batch=8 / imgsz=480`，存档里跑出 0.745 的那次是
`batch=72 / imgsz=480`。而 `batch=48 × imgsz=640` 的像素单位是 19.66M，
比已验证的 16.59M 高 18%——在 8 GB 的 RTX 4060 Laptop 上几乎必然溢出。
**这才是那次点击真正废掉的东西**，跟磁盘无关。

守卫的模型：峰值显存正比于 `batch × imgsz²`，比例常数标定自那个唯一跑完且
指标可信的现场：

```
px_budget(total_mb) = total_mb × (72 × 480²) / 8188
```

于是 `imgsz=640` 时上限是 40，`imgsz=480` 时是 72——**标定点不会被自己的守卫
拒掉**，这条专门写了断言：守卫要是比它保护的东西还严格，等于把项目唯一可信的
配置挡在门外。

超预算在**起进程之前**返回 400，并给出可照做的建议：

```
batch=48 × imgsz=640 需要 19.66M 像素单位，超过本机 8188 MB 显存的预算 16.59M。
本机已验证的上限是 batch=72 × imgsz=480(...)；imgsz=640 时 batch 最多 40。
```

前端接 `GET /api/train/limits?imgsz=&device=`，在表单里提前显示上限；超限时
批量输入框转明火色、开始按钮禁用。后端仍是唯一裁判。

**CPU 或探测不到显卡时不拦**：探测失败是环境问题，不该变成训练的拦路石。

## 追加：停止训练的状态机漏洞

用户报告：点「停止」，再点「开始训练」，提示 `GPU 正被「train」占用`。

### 先看状态，再看代码

直接查运行中的服务：`gpu_job.busy = false`、锁是空的。也就是说**此刻**没有卡住
——bug 是时间窗里的，不是永久卡死。任务历史里有一次 `epochs=10` 的 11:16 运行，
`started_at 11:16:46`、`finished_at 11:24:06`、`returncode 1`、`error` 为空。

### 根因：`stop()` 根本没有改状态

```python
def stop(self, job_id: str) -> bool:
    ...
    job.add_event({...})
    job._proc.terminate()   # ← 只做了这一件事
    return True
```

状态留给后台 `_reap` 线程去改。于是在「点了停止」到「进程真正退出」之间，
`manager.running()` 仍然返回这个任务，`start()` 的第一道判断就把新训练挡了：

```python
if self.running() is not None:
    raise deps.GpuBusy("train")   # → 「GPU 正被「train」占用」
```

三个各自独立的问题叠在一起：

1. **状态没同步挪走**。停止意图没有任何representation，窗口多长取决于进程多久死。
2. **被强杀的进程记成 `failed`**。Windows 上 `TerminateProcess` 返回退出码 1，
   而 `_reap` 按「退出码非零」判定失败，界面显示「失败 · 退出码 1」——一次正常
   停止被报成故障。前端 `JobStatus` 里早就写了 `'stopped'`，**后端从来没产生过
   这个值**，实现漏了。
3. **只杀直接子进程**。`Popen.terminate()` 走 TerminateProcess，只作用于直接子
   进程；DataLoader 的 `workers` 个子进程变成孤儿，继续占着显存和数据管道。

### 改法

状态机补上 `stopping` / `stopped` 两个状态，`ACTIVE_STATUSES` 与
`TERMINAL_STATUSES` 分开：

- `stop()` **同步**置 `stopping` 再起后台线程收尾；`running()` 把 `stopping`
  也算「占用」——进程树还没死、显存还没还回来，此时放行新训练就是等着 OOM
- 停止期间再启动仍返回 409，但 `detail` 说清是「训练 xxx（正在停止，几秒内释放）」
- `_reap` 按**停止意图**判定为 `stopped`，不再按退出码误判为 `failed`
- 结束**整棵进程树**（Windows `taskkill /F /T`，POSIX 退化为 `terminate`）
- SSE 的收流判据从「状态 != running」改成「状态 ∈ 终态集合」。否则 `stopping`
  一出现就收流，界面会在进程树还没死时显示「已停止」

前端同步：状态条加 `stopping` 分支（中性色，不用明火色——它不是故障）、按钮
禁用并改文案、点击停止后**乐观**置为 stopping，不等 SSE 回包。

### 端到端验证（真 HTTP，不是单测）

用 `device=cpu` 跑，避免和正在进行的探针实验抢显存：

```
1. POST /api/train/jobs           → 201, status=running
2. POST /api/train/jobs/{id}/stop → {"stopped": true}
3. GET  /api/train/jobs（立刻）    → status=stopping, stop_requested_at 有值, error 为空
4. POST /api/train/jobs（立刻）    → 409
      detail: GPU 正被「训练 68dd49f8c360（正在停止，几秒内释放）」占用
5. 等待收尾                        → status=stopped, returncode=1, error 为空, 用时 0.6s
6. POST /api/train/jobs（收尾后）  → 201
```

第 3、4 步就是用户遇到的场景。仍然返回 409 是**对的**——显存还没还回来；改的是
窗口长度（0.6 秒）和提示的可读性。

### 截图又抓到一条自己写的 bug

按项目惯例给「停止中」状态拍了一张（这个状态只存在几百毫秒，用
`page.route` 掐断 SSE 才截得到）。图里发现：**设备已经选到 CPU，显存提示却还在
显示 GPU 的「批量上限 162」**。

原因是 `imgsz` 与 `device` 各触发一次 `/api/train/limits`，返回顺序不保证，慢的
那次覆盖了快的结果。危害不只是显示错：`overBudget` 会据此**禁掉一个 CPU 下完全
合法的配置**（比如 imgsz=1280 batch=16，GPU 上限算出来是 10）。加请求序号守卫，
只采纳最后一次发出的请求，并补了一条常驻 E2E（`vram-hint.spec.ts`）锁住它——
单独一个文件，因为 `training.spec.ts` 整份会被 `beforeEach` 跳过。

> 单元测试全绿、接口断言全对，问题只在截图里。
