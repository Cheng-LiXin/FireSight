# 2026-09-28 · 新数据首训：0.7928，以及「旧归档的 0.8626 是假的」

> 一次训练跑完，看起来是「新数据比旧数据差 0.07」。**这个读法是错的。**
> 本文记录为什么错，以及真正该拿什么当新标尺。

---

## 一、这次跑了什么

`20260928-165715-D-Fire-raw-yolo11s`（用户自己起的，我只做分析）：

| 项 | 值 |
|---|---|
| 数据集 | `D-Fire/raw`（新，提供方切分：train 14122 / val 3099 / test 4306） |
| 模型 | yolo11s |
| 几何 | imgsz 640 · batch 20 |
| 轮数 | 配置 `epochs=100`，`patience=10` 早停，实跑到 **82 轮** |
| 归档 | mAP@50 **0.7923** / mAP@50-95 **0.4707** / P 0.789 / R 0.733 |
| 耗时 | `time` 列 15081.5 s ≈ 4.2 小时（255.6 s/轮，含每轮验证） |

用户把 batch 从 16 提到 20、轮数从 50 提到 100（耐心值 10）。**这两个改动是我们之前的建议
与他自己的判断的混合**，分析时必须记住——它不是一个受控实验。

### 曲线（每 10 轮）

| epoch | mAP@50 | mAP@50-95 |
|---|---|---|
| 10 | 0.6282 | 0.3282 |
| 20 | 0.7142 | 0.3939 |
| 30 | 0.7550 | 0.4356 |
| 40 | 0.7812 | 0.4584 |
| 50 | 0.7854 | 0.4646 |
| 60 | 0.7922 | 0.4683 |
| 70 | **0.7933** | 0.4703 |
| 82 | 0.7922 | 0.4690 |

**早停判据算错了。** `patience=10` 用的是 **mAP50-95 的 fitness**，它的最好值是 epoch 72
（0.47081），末次改善后 **10 轮没有任何改善** → epoch 82 触发早停，合法。

但**按 mAP@50 看，最好值在 epoch 62（0.79391），之后 20 轮都在 0.7918–0.7936 里抖**。
也就是说：**这次早停并不是「练不动了」，而是被 fitness 口径停在了早已平台期的一段噪声里。**

配合看 70 之后：72 的 0.47081 之后再没超过 → 确实收敛了。
**结论：100 轮的预算没有被浪费，但 82 轮和 62 轮的结果统计上无差别。**

## 二、决定性发现：旧归档的 0.8626 是「虚高」，不能用来比

同一场地、同一批图，两个模型在**新 val（3099 张）**上评估：

| 模型 | 训练数据 | 训练时自报 mAP@50 | **在新 val 上评** | Δ |
|---|---|---|---|---|
| `20260928-165715`（新） | `D-Fire/raw` | 0.7923 | **0.7928** | +0.0005 |
| `20260927-204643`（旧） | `D-Fire/train` | 0.7897 | **0.8626** | **+0.0729** |

**新模型的 0.7923 与 0.7928 几乎完全一致**——这是应该的：它训练时用的 val 与新 val 是同一份。

**旧模型在新 val 上凭空高出 0.073。** 这就是「旧数据泄漏」的量化形态，而且**比之前估的还大**：
- 之前用 dHash 估的是「21.1% 的 val 图能在 train 里找到近重复」（最小汉明距离 ≤0）；
- 现在这个是**指标层面**的直接证据：多出来的 0.0729 就是那批重复图贡献的。

对照：旧模型在**旧** val 上的自报是 0.7897。所以
**0.7897（旧 val 自报）≈ 0.7928（新 val 上评新模型）= 真实水平**，
而 **0.8626 是泄漏撑起来的**。

> 换句话说：**换数据集没有让模型变差，只是把之前一直虚高的读数打回了真值。**
> 我们上一轮说「旧归档在新 val 上会虚高、所以整个作废」——现在有了数字：**虚高 +0.0729**。

### 逐类（mAP@50-95）

| 模型 | smoke | fire |
|---|---|---|
| 新（raw） | 0.5335 | 0.4053 |
| 旧（train），新 val 上评 | 0.6353 | 0.4816 |

泄漏对**两类都抬高**，smoke 抬得更多（+0.102 vs +0.076）。合理——静态机位的烟雾
背景几乎不变，近重复帧里最容易「记住」。

## 三、新模型的真实水平：比旧模型的真实水平略好

拿**各自训练时自报的数**比（这是两边唯一口径一致的一组）：

| | 旧（`D-Fire/train`, 50轮, b16） | 新（`D-Fire/raw`, 82轮, b20） |
|---|---|---|
| mAP@50 | 0.7897 | **0.7923** |
| mAP@50-95 | 0.4569 | **0.4707** |
| P | — | 0.789 |
| R | — | 0.733 |

**Δ mAP@50 = +0.0026（噪声级）· Δ mAP@50-95 = +0.0138（真实改善）。**

这个模式很干净：mAP@50 早就饱和了（0.79 附近），**换数据集 + 加轮次真正买到的是定位精度**
（mAP@50-95），不是「检没检到」。这也与 P0-1 的结论一致——饱和之后，
**继续堆容量/轮数买的是 mAP50-95**。

⚠️ 但注意：这两组**不完全可比**（52% 的 train 图是重合的，且 batch 20 vs 16、
82 轮 vs 50 轮都变了）。所以这个 +0.0138 只能说「方向对」，不能说「就是数据集换代带来的」。

## 四、和上一轮 s 容量的关系

旧数据上的结论是：容量 n→s 在同预算下 **+0.0272 mAP@50**（后 15 轮 15/15）。
新数据上**还没做 n 的对照**，所以「新数据上是否仍值得用 s」**没有数据**。

不过有一个侧面信号：新 run 用 s / 640 / b20 跑到 0.7923，而**旧 n / 640 / b40 / 50 轮**
在新 val 上会是多少、在旧 val 上是 0.7675——**跨数据集的这两个数不能比**。
要回答「新数据上 s 值不值」，只能在新数据上补一次 n。

## 五、两件立刻该记下的副作用

1. **「当前权重」是自动回落到最新归档的**（`source=fallback-newest`）。
   新归档一落盘，`models/active.json` 不存在时服务就自动用它了——**没有经过我或用户的确认**。
   现在识别页用的就是这个新模型。这是 v1.6.0 定下的行为（用户指定优先、没指定就用最新），
   但**每次有新归档落盘都会静默换线上模型**，值得在界面上提示一句。
2. **旧现场 `20260927-204643` 的 `args.yaml` 里 `model` 已被改写成 `last.pt`**
   （ultralytics 续训的副作用，上一轮已知）。这次它不影响我们，因为对比评估直接用归档权重。

## 六、下一步该做什么（按性价比排序）

### 1. 建立新标尺：在新数据上跑一次 n（**必做**）
现在新数据上只有 s 一个点。没有 n，就**没法回答「新数据上还该不该用 s」**——
而这是这次换代最该重新验证的结论。配置：`yolo11n` / 640 / **batch 与 s 那次一致或按显存最大化**
/ 同样 `patience=10` / `epochs=100`。代价约 2 小时（n 比 s 快约 1.7×）。

**注意**：要与本次可比，n 那次的 **batch 和 epochs 必须与 s 一致**，否则又变成不可比。

### 2. 用 test 出一组最终数字
`val` 已经反复用于决策（选模型、比数据集），**它已经被「用脏」了**。
`test`（4306 张）一次没用过。现在两个模型都归档了，应该：
**用 test 评一次新模型**，得到一组「没有参与过任何决策」的数作为最终汇报口径。
这正是当初设 `split=val|test` 的原因。

### 3. 别再往上堆轮数
82 轮里 62–82 是平台期，20 轮换来 0.0003 的 mAP@50。**下一位接手的人不要再加 epochs。**

### 4. 可以考虑的（按价值递减）
- **batch 20 是否已到顶**：用户把 16 提到 20，实跑峰值显存待查（本次没测）。
  若还有余量，试 batch 24（但收益可能很小）。
- **容量继续往上（m）**：8 GB 卡上 s@640 已经是贴着上限跑（b20），m 会掉到个位数 batch，
  训练时间会难看。**不建议**。
- **分辨率**：P0-1 已证 640→960 是负收益（−0.0090），**不要动**。

## 七、一句话

**新模型 0.7928 是真实水平；旧模型的 0.8626 是泄漏撑起来的假象。**
换数据集不是退步，是把一直虚高的读数打回了真值——并且在新数据上，
**mAP@50 已饱和、真正改善的是 mAP@50-95（+0.0138）**。
下一步：在新数据上补一次 **n** 的对照，然后用 **test** 出一组干净的最终数。
