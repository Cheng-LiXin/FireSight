# 一、浅色主题重做

## 起因

用户要求把主题从暗色「热成像取景」改成现代简约浅色，并明确要**多轮确认**。

现有配色不是随手挑的：类别色 `#00A3C4` / `#D14A17` 在暗底 `#221C15` 下过了六项校验
（明度带、彩度下限、CVD 分离 deutan ΔE 21.1、常视觉 30.8、对比度）。所以第一步不是
改色，而是**把浅底上的代价量出来**。

## 硬约束一：烟色在浅底上不达标

按「数据色 ≥3:1 / 正文 ≥4.5:1」审计 `#F7F8FA`：

| 令牌 | 值 | 对比度 | |
|---|---|---|---|
| `--cat-smoke` | `#00A3C4` | **2.81** | ✗ 必须改 |
| `--cat-fire` | `#D14A17` | 4.20 | ✓ |
| `--fire-3`（焦点框/滑块/风险 alert） | `#FF9A3C` | 1.99 | ✗ |
| `--fire-4` | `#FFE9A8` | 1.13 | ✗ |
| `--dross`（12px 文字） | `#8C8172` | 3.59 | ✗ 正文要 4.5 |
| **训练曲线 4 色板** | — | 3.05–3.77 | ✓ 可原样保留 |

## 硬约束二：校验器已经不存在了

`palette.ts` 一直写着「改动必须重跑 `node <dataviz>/scripts/validate_palette.js`」，
但那个工具在 `.dsh` / `.claude` / `.codex` / `D:\Program` / `references` **全域搜索无果**。
也就是说这条纪律实际上已经无法执行——只是没人发现。

**反推 + 自检**：按它记录的两组已知值试算了 4 种度量 × 3 种 CVD 模拟共 12 种组合，
只有一组同时命中两个数：

```
ΔE = 100 × ‖OKLab(a) − OKLab(b)‖   +   Machado 2009 severity 1.0
```

| 自检向量 | 记录值 | 复现 |
|---|---|---|
| 类别色 常视觉 ΔE | 30.8 | **30.8** |
| 类别色 deutan ΔE | 21.1 | 21.2 |
| 训练板 最差相邻 deutan ΔE | 13.0 | **13.0** |
| 训练板 最差相邻 常视觉 ΔE | 21.6 | **21.6** |

第二次自检还顺带验证了注释里那句警告：把绿与琥珀排到相邻，deutan ΔE 确实掉到 5.9
（注释写的是 4）。**先能复现已知结论，再用它做新决策**——否则算出来的数字只是自说自话。

## 多轮确认里被数据推翻的两个判断

### 1. 「烟=浅灰 + 火=告警红」不成立

用户选了「保留唯一一个告警红」，我第一版就落成 `烟 #6B7280 + 火 #D14A17`。看起来没问题，
测出来却是：

```
常视觉 ΔE 20.1   deutan 15.6   protan 13.4
```

**比原基线 21.1 还差。** 原因是两者的**明度几乎相同**（0.551 vs 0.589），而灰与红在红绿色盲
下主要靠明度分离。扫了一遍灰阶梯度后压到 `#1F2937`（L 0.278）：

```
常视觉 37.2   deutan 36.3   protan 25.1        ← 三条通道全部优于基线
```

> 教训：**「看起来能分开」和「色觉缺陷下能分开」是两件事。** 这条已写进 `tokens.css`
> 注释，防止后人凭观感把烟色改浅。

### 2. 灰阶撑不起 4 条曲线

用户说「曲线用更显眼的颜色」，而更早的选择是「整个主题改灰白黑」。我先按纯灰阶做了
「两级灰 × 实线/虚线」跑通，但实测：

```
#FFFFFF 上对比度 >=3:1 的灰只有 5 档
相邻 ΔE 最小 6.8（要 >=13 才算可区分）
```

**「要够对比就得够深，够深了彼此就分不开」**——这是灰阶的硬限制，不是选色技巧问题。
所以训练曲线保留彩色，但**沿用原 4 色板的色相**、只为白底重调明度彩度：

| | 原（暗底） | 新（白底） |
|---|---|---|
| 对比度 | 3.24–4.01 | **3.58–7.61** |
| 相邻最差 deutan ΔE | 13.0 | **21.8** |

顺带把 `--fire-1/2/3` 按角色重命名为 `--accent*`（单色主题里继续叫 fire 就是撒谎），
删掉一个引用点都没有的 `--smoke-1..4` 与 `--fire-4`。**只做浅色**，暗色模式整块删除。

# 二、P0-1 分辨率探针

## 问题与判据

上游分析发现：fire 的中位框边长只占画面 **7.1%**、65% 的框面积 <1%，而 D-Fire 原图主流是
1280×720——`imgsz=640` 仍在做 2 倍线性降采样。所以问：**继续加分辨率还有收益吗？**
预定判据：mAP50 明显为正（>+0.02）→ 值得跑满 50 轮；基本持平 → 停手，转模型容量或数据侧。

## 为什么两组都必须真跑

不能拿 50 轮那次的第 14 轮当对照：`lrf=0.01` 按 `epochs` 线性衰减，50 轮跑到第 14 轮时 lr
还有 `lr0×0.73`，而 15 轮跑完时已降到 `lr0×0.01`。**学习率轨迹不同，两个数字不可比。**
两组都用 `epochs=15` 启动，于是直接比第 14 轮就成立。

（第一组 `probe-640x40` 在第 15 轮中途被外部硬杀，日志无异常；前 14 轮完整落盘，
第 14 轮就是「15 轮计划下的第 14 轮」，所以不需要补跑，省了 26 分钟。）

## 结果：960 没有赢

| | 640x40 | 960x16 | Δ |
|---|---|---|---|
| mAP50 @14（训练期验证，conf=0.001） | 0.70515 | 0.69767 | **-0.0075** |
| mAP50-95 @14 | 0.38982 | 0.38305 | -0.0068 |
| 配对差（14 轮）均值 | | | **-0.0090** |
| t 值 | | | **-1.14**（\|t\|<2 即不可区分） |
| 960 更好的轮数 | | | 6/14 |
| 每轮耗时 | 93 秒 | 205 秒 | **2.21×** |

输入尺度**——换回 640 推理就掉，且掉得比训练期验证显示的更多。

## 结论

**分辨率杠杆已经到头。** 提高训练分辨率既没有收益，还会让模型在低分辨率推理下变差，
而代价是 2.2 倍训练时间（50 轮：77 分钟 → 171 分钟）。按预定判据应**停手**，
下一个杠杆转向**模型容量**（yolo11n → yolo11s）或数据侧。

> 附带说明：显存守卫的常数是在 **yolo11n** 上标定的，只看 `batch × imgsz²`，
> **不含模型规模项**。换 yolo11s/m 时真实显存需求更高，守卫可能放行一个会 OOM 的 batch。
> 换大模型前需要给守卫加参数规模因子，或先手动降一档。

# 三、顺带发现的 bug：评估口径与归档不可比

交叉评测报出 `mAP50 = 0.5831`，而同一个权重的 `metrics.txt` 记的是 `0.7052`。
**差 0.12 不是模型问题，是阈值口径不一致：**

| 路径 | conf | iou |
|---|---|---|
| 训练期验证（写进 `metrics.txt`） | `null` → ultralytics 兜底 **0.001** | **0.7** |
| `fs-val` / `evaluate_weights` | `ValConfig` 默认 **0.25** | **0.6** |

`validator.py` 的兜底是 `self.args.conf = 0.001`，但**只在 conf 为 None 时生效**——
而评估路径显式传了 0.25。

后果：`fs-val` 系统性低报，而且**同一份权重会给出两个不同的 mAP**。ROADMAP 里计划的
「模型库 · 多权重对比评估」正是要调 `evaluate_weights`——上线后会直接暴露成
「归档说 0.767，对比工具说 0.58」。

**已修**：`ValConfig` 的 `conf` / `iou` 默认改为 **0.001 / 0.7**（mAP 计算口径），
部署阈值仍归 `InferConfig`（0.25 / 0.6），两侧不再混用；`fs-val` CLI 默认同步；
补了回归断言锁住这两个默认值。

# 四、这次我自己踩的坑

## 1. 把一个多进程错误误判成「管道缓冲」

交叉评测卡住 16 分钟、CPU 只用了 3.4 秒。我据此判断是 PowerShell 管道缓冲被 ultralytics
的进度条塞满，改成写文件重跑——**又卡住了**。真因是脚本缺 `if __name__ == "__main__":`：

```
RuntimeError: An attempt has been made to start a new process before the
current process has finished its bootstrapping phase.
```

Windows 上 torch 的 DataLoader 走 **spawn**，worker 会**重新导入主模块**；工作写在模块顶层
就等于每个 worker 再跑一遍整个脚本 → 递归起进程。日志里那段标题出现两次就是证据
（我第一遍没细看日志内容，只看了 CPU 占用，于是编出了一个听起来合理的解释）。

> **异常信息在日志里，先去读日志，别先看资源占用就下结论。**
> 另外那次 `python -`（从 stdin 读代码）反而"侥幸能跑"，因为 spawn 无法重新导入
> stdin 形式的 `__main__`——所以「上次这样跑通过」不构成「这次也会通过」。
> `train_worker.py` 与探针脚本一直有守卫，那条路径没问题。

## 2. 测试夹具把临时文件撒进了仓库根

`tests/test_20_job_stop.py` 里 `monkeypatch.setattr(jobs, "RUNTIME_TMP_DIR", Path("."))`——
`Path(".")` 是 pytest 的 CWD，也就是仓库根。跑一次测试就在根目录留下一个
`firesight-train-<id>.json`，一次跑了 24 个。改为 `tmp_path`。

> 夹具里写路径，**不要用 `Path(".")`**；能用 `tmp_path` 就用 `tmp_path`。

## 3. 中断一个工具调用，连带杀掉了后台任务

探针跑到第 15 轮中途被硬杀（日志无异常、后台任务记录同时消失）。当时我正在发一个
很慢的工具调用并被中断。**教训：跑长任务期间不要发会中断的调用。**
另外这也说明：**长任务要能从中断中恢复**。这次的恢复成本很低，因为 `results.csv` 是逐轮
落盘的——第 14 轮数据完好，不需要重跑。
