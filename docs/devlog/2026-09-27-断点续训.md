## 一、先说清「暂停」这个动作本身

停止流程（v1.3.2）只做一件事：`taskkill /F /T` 杀掉进程树。它**不归档、不删除**，
而「强杀」恰好意味着 ultralytics 走不到 `final_eval()`——于是
`strip_optimizer(last)` 不会执行，`last.pt` 保留完整训练态。

**所以「能续训」不是这次新做的前提，而是一直就在**：现场里那份 54.3 MB 的
`last.pt` 里躺着 `optimizer` / `ema` / `scaler` / `updates` / 完整的 `train_args`。
缺的只是**入口**——在此之前「停止」等于进度全丢，只能从头再来 50 轮。

暂停前先核实了这件事（只读）：

| 键 | 值 | 含义 |
|---|---|---|
| `epoch` | 39 | 0-based → 已完成 40 轮 |
| `optimizer` | 有 | 优化器状态在 |
| `ema` | 有 | EMA 权重在 |
| `scaler` | 有 | AMP scaler 在 |
| `updates` | 9220 | 优化器步数 |
| `train_args.epochs` | 50 | 续训的目标轮数 |

## 二、实现：四处「不能照直觉写」的地方

### 2.1 跑完的现场**不能**续训

`Trainer.final_eval()` 里有一行 `strip_optimizer(self.last)`。所以：

| 现场状态 | `last.pt` 大小 | 含优化器 | 能续吗 |
|---|---|---|---|
| 被停止 / 崩溃 | 20.3 MB（≈4× 裸模型） | 是 | ✅ 真续训 |
| 暂停中（本次） | 54.3 MB（yolo11s 更大） | 是 | ✅ |
| 已跑完 | 5.2 MB（≈裸模型） | 否 | ❌ |

从剥离过的检查点接着练会**重置优化器、EMA 与调度器**，学习率轨迹接不上——
那是换个权重微调，不是续训。**这个区别必须让用户看见**，所以：

- 列表里 `resumable=false` 时给的是**原因**（悬停可见），不是说不清的灰按钮
- 接口对该情况返回 **400 并说明**

### 2.2 配置以检查点为准，不是请求

`Trainer.check_resume()`：

```python
self.args = get_cfg(ckpt_args)          # 用检查点里的 train_args 重建整个配置
for k in ("imgsz","batch","device","workers","cache","patience","val","plots","save_dir",…):
    if k in overrides:                  # 只有显式传了的白名单项才覆盖
        setattr(self.args, k, overrides[k])
```

所以续训的载荷是**最小的**：只给现场（+ 可选 `device`）。前端类型也单独定义
（`TrainResumeRequest`），**不**把正常训练那些字段标成可选——标了就会让人以为
「填了就能改几何」，而它其实不生效。

### 2.3 `imgsz` 必须显式传（这条从外面完全看不出来）

加载权重时：

```python
include = {"imgsz", "data", "task", "single_cls"}   # Model._reset_ckpt_args
```

也就是 `self.overrides` 里**带着该权重的 `imgsz`**，而 `imgsz` 在可覆盖白名单里。
不显式传检查点的 `imgsz`，它就会被加载权重的值盖掉。实测：加载 `yolo11s.pt` 时
`m.overrides = {data, imgsz: 640, model, single_cls, task}`。

对本次（检查点也是 640）看不出差别——这正是它危险的地方：换个 imgsz 训练过的现场
就会静默变形。所以代码里显式传，并写明原因。

### 2.4 守卫要按检查点的模型判

续训请求里的 `model` 默认是 `yolo11n.pt`，而实际在训的是检查点里的 yolo11s。
按请求判会拿 **yolo11n 的额度**放行一个 yolo11s 的续训——实测规模因子差 1.82 倍。
所以守卫读检查点的 `imgsz/batch/model`。

## 三、验证：真续训一次，不靠 mock

对一个停在 40/50 轮的现场发起续训（请求只给 `dataset` + `resume_run_id` + `device`）：

| 证据 | 结果 |
|---|---|
| `results.csv` | 40 → **41** 轮，新行 `epoch=41`（末三行 39/40/41）→ **追加**且轮次连续 |
| 现场目录数 | 不变（11）→ **没有另开目录**（若开错目录这里会 +1） |
| `last.pt` | `epoch=40`（→ 已完成 41 轮）、`updates` 9220 → **9436**（优化器步数延续） |
| 几何来源 | `imgsz=640 / batch=16 / model=yolo11s` 全部取自检查点 |
| 耗时 | 第 41 轮 170 秒——与暂停前的节奏一致（没有退化） |

「轮次是 41」这一点是决定性的：一次新训练即使复用同名目录（`exist_ok=True`）也会
**重写** `results.csv` 并从第 1 轮开始。出现 41 就只能是接着练。

验证完按用户要求**再停回去**，现场仍是 `resumable=True, 41/50`。

## 四、界面

训练记录的每一行：能续的给「继续训练」按钮（`title` 写明「已完成 41/50 轮，
从第 42 轮继续」），不能续的给「不可续训」+ 悬停原因。

点击时会 `window.confirm` 确认一次——**这是有意的**：误点一次就是几十分钟的
GPU 占用，而项目里没有自定义弹窗组件。确认文案说明「几何与总轮数取自检查点，
不能在这里改」，把 2.2 那条约束在执行前就告诉用户。

> 前端类型单独定义 `TrainResumeRequest` 而不是复用 `TrainJobRequest`：
> 续训只需要两个字段，复用会逼着调用方填一堆不生效的值。

## 五、这一轮我犯的错

**Edit 的 `old_string` 只删了一个换行，把函数体挤到了 `def` 同一行。**
`def _num(...) -> Optional[float]:    raw = metrics.get(key)` —— 语法上竟然成立，
于是紧随其后的 `    if raw in (...)` 变成「意外的缩进」，报错指在 136 行而不是
真正被改的那一行。**构建/导入检查这次救了场**（如果先跑测试，报错会出现在更远的地方）。

这已经是同一个毛病的第二次：上一次是把 `<thead><tr>` 一起框进去删掉了。
**改单行时 `old_string` 就只框那一行**，不要顺手带上相邻的换行与结构。

## 七、遗留

- **续训改不了总轮数**（`epochs` 不在白名单里）。想多跑几十轮得开新训练——这是
  ultralytics 的语义，不是我们偷懒。要支持「续训并延长」，得自己改 `train_args`
  再写回检查点，属于动 checkpoint 的手术。
- **正在训练的那个现场也会显示「继续训练」**（列表不知道哪个 run 是当前任务）。
  点了会被 GPU 锁挡成 409，提示可读，但按钮本可以是禁用的。要修得让 job 从启动时
  就知道自己的 run_id——现在它只在收到 `done` 事件后才有。
  **→ 已在 2026-10-09 修掉，见 [`2026-10-09-暂停与续训按钮区.md`](2026-10-09-暂停与续训按钮区.md)。**
- 任务表在内存里：**服务重启后任务记录清空**，但现场与检查点都在磁盘上，
  所以续训不受影响（这正是断点续训的价值）。

## 八、补记：一个「第二次才坏」的 bug（真的用起来时才暴露）

实现完、自己验证过一次之后，用户点「继续训练」却被**守卫拒了**：

```
batch=16 × imgsz=640 在 last 上需要 25.10M 等效像素单位，超过预算 16.59M。
模型 last 没有实测数据，按 yolo11m 的 3.83 倍估算……imgsz=640 时 batch 最多 10
```

`模型 last` —— 模型名被认成了 `last`。根因是 ultralytics 这条行为：

```python
# Trainer.check_resume()
self.args.model = self.args.resume = str(last)   # 把 model 改写成 .../weights/last.pt
```

**续训一次之后，检查点里的 `train_args.model` 就被改写成 `last.pt` 了。**
于是第二次续训从检查点读到 `last` → 守卫按未知模型（yolo11m 的 3.83 倍）估 →
一个本来合法的 batch 被判超预算。**守卫逻辑是对的，喂给它的模型名是错的。**

这是「看起来能用、第二次才坏」的典型：第一次续训完全正常（检查点里还是
`yolo11s.pt`），而**那次完成时**被改写——所以我的验证碰不到它，用户一用就碰到。

**修法**：模型名优先从 `run_id` 的末段取。`make_run_id(dataset, model)` 拼出来的
run_id 末段就是模型主名（`20260927-204643-D-Fire-train-yolo11s` → `yolo11s`），
而且它**不会随检查点被改写**。检查点的字段只在 run_id 末段不是已知模型时才退回使用。

补了两条回归测试：一条造「`train_args.model` 已被改写成 `last.pt`」的检查点，
断言续训仍认出 `yolo11s`（**修复前这条会 400**）；一条覆盖 `_checkpoint_model`
的三种取值路径。

> 教训：**「验证过」不等于「用起来没问题」。** 我的验证动作本身会污染下一次的前提
> （发起一次续训 → 检查点被改写）。凡是「操作会改变自己的输入」的功能，
> 验证必须**跑第二遍**。
