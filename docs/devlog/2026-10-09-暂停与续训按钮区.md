# 2026-10-09 · 暂停与续训收进一个按钮区

> 前一篇见 [`2026-09-28-新数据首训与泄漏的量化.md`](2026-09-28-新数据首训与泄漏的量化.md)。

## 一、用户的原话与它暴露的问题

> 「完善断点续训功能（前端开始训练后，由『暂停训练』按钮控制）」

v1.7.0 已经把续训做出来了，机制是通的（真机验证过 40/50 → 41 轮、优化器步数延续）。
问题在**入口的位置**：续训按钮长在下面那张训练记录表里，而用户刚点完的是上面按钮区里的
「停止」。他得自己往下滚、在十几行记录里找到自己刚跑的那一行、再点一次。

而且——**那一行的按钮点不动**。因为 `job.run_id` 只在收到 `done` 事件时才赋值
（`api/jobs.py` 的 `_absorb`），被暂停的任务永远走不到 `done`。前端根本不知道
该续哪个现场。这不是「按钮放错地方」，是**数据链断了一环**。

interview 定下的方向：

| 问题 | 用户的选择 |
|---|---|
| 按钮区怎么做 | **A：开始 / 暂停 / 继续 配对成组**，同一位置依次长出；表格里那行保留 |
| 崩溃后要不要给路 | **要**。崩在第 30 轮的现场和暂停留下的一模一样（`last.pt` 带优化器状态） |
| 第 1 轮没跑完就暂停 | 显示**禁用的**按钮 + 原因，**不要藏起来** |
| 「停止监控」要不要一起改 | 不动。训练页只改文案与状态条 |
| 接口路径要不要改名 | 不改，`POST /api/train/jobs/{id}/stop` 原样保留 |

## 二、第一处反直觉：run_id 必须**开训前**就报上来

后端原来的顺序是：子进程跑完 → 发 `done`（带 `run_id`）→ 父进程 `job.run_id = ...`。

暂停这条路上没有 `done`。所以改法是：**训练子进程在开训前就把现场名报上来**。

- `_train_fresh` 里 run_id 在 `model.train()` **之前**就已经算出来了（`exp` 兜底之后）
- `_train_from_checkpoint` 里从检查点的 `info["name"]` 读得到
- 两处都插一句 `_notify_run(on_run, run_id)`，`train_yolo()` 因此多一个可选 `on_run` 回调
- 协议多一个事件类型：`{"type":"run","run_id":"…"}`
- `_absorb` 加 `elif kind == "run": job.run_id = event.get("run_id") or job.run_id`

判据写进了测试，而且是**顺序判据**而不是「有没有被调用」：假 `YOLO` 的 `train()`
里回看已收到的 run_id 列表，走到 train 时它必须已经非空。

```python
def train(self, **kwargs):
    self._log.append(("train", list(self._seen)))   # 这一行就是判据
```

### 那为什么不猜「最近改动的现场」

被暂停的任务完全可以靠「`runs/training/` 下最近改动的目录」反推，不用改协议。
没这么做：训练中 `results.csv` **每轮都在写**，目录 mtime 一直在动，那个值随时可能是
别人刚跑完的现场。猜错就是把用户的进度接到另一个实验上——比多点一次按钮严重得多。
多一个事件类型是明确、可测的代价。

---

## 三、第二处反直觉：上报的是**现场目录名**，不是归档名

`runs/training/` 下那一层才叫 run_id。没设 `experiment` 时，它和归档名恰好相同；
设了 `experiment` 时就不同，而 `resume_run_id` 认的是**前者**。

界面上的模板里 `experiment` 默认是空的，所以这条路径平时走不到——只在有人手填实验名时
才暴露，然后界面会拿一个不存在的现场去续训。代码注释里把这句话写死了，测试里也分别
覆盖了「设了 experiment」与「没设」两种。

---

## 四、第三处：回调抛异常不能毁掉训练

上报走的是子进程 → 父进程的管道。管道断了、父进程先退出、编码出错，都可能抛。
一次训练几十分钟，为了报个名字把它搞崩是荒谬的取舍：

```python
try:
    on_run(run_id)
except Exception:
    logger.exception("上报 run_id 失败（不中断训练）")
```

整条吞掉并记日志。另外 `done` 事件不再抹掉已经报过的 `run_id`
（`event.get("run_id") or job.run_id`）——子进程收尾时那条 `done` 不带 run_id 的话，
界面刚拿到的现场名会被清空。

## 五、界面：三个按钮，其实是同一件事的三阶段

```
[开始训练]                    →  训练还没起（或已收尾且无可续现场）
[训练进行中…] [暂停训练]       →  跑着呢
[开始训练]        [继续训练]   →  收尾了，现场还在
```

`「暂停训练」`这个名字是有意的。后端的接口**确实不是挂起**，是 `taskkill /F /T`
把整棵进程树结束掉（只杀直接子进程会留下 DataLoader 的 workers 变孤儿占显存）。
但现场留得住：`last.pt` 带着优化器状态、`results.csv` 已追加到第 N 轮，
下一次从第 N+1 轮接上——**从用户的角度这就是暂停**。所以按钮叫暂停，
接口路径 `.../stop` 没改（改它要动 e2e 与文档，收益为零）。

崩溃（`failed`）走同一套：崩在第 30 轮的现场和暂停留下的一模一样，能续就该给路。
只是文案分开——暂停是「已暂停 · 现场保留」，崩溃是「失败 · 退出码 1 · 现场可续」。
两种收尾给同一句话是错的：崩溃的人想知道「现场还能不能用」，暂停的人想知道「东西还在不在」。

**不能续时保留按钮但禁用**，原因挂在 `title` 上。藏起来的话用户看到的是
「上次崩了，然后什么都没有」。

### 第 1 轮都没跑完就暂停

`results.csv` 和 `last.pt` 都是**第 1 轮结束时才首次落盘**。所以有一个窗口：
训练起来了、GPU 占上了、然后被暂停 → `runs/` 下连这个现场的目录都没有。

这时的呈现不是「出错」，是**禁用的按钮 + 一句原因**：

> 第 1 轮未跑完，没有留下检查点

判据是「`job.run_id` 拿到了、但训练记录里找不到这一条」——两者分别对应
「训练开跑了」与「现场成形了」，中间那一段就是这个窗口。

### 前端（新增 2 条 e2e）

`apps/web/e2e/resume.spec.ts` 4 → **6 条**。两条按钮区用例 **不真跑训练**：
`page.route` 拦掉 `POST /api/train/jobs` 与 SSE 流，自己按协议发 `start`/`run`/`error`，
断言按钮文案、禁用状态与 `title` 上的原因。真训练由 `training.spec.ts` 里那条
门控用例负责（几十分钟、有副作用，不能混进常规回归）。

> 拦 SSE 这条要小心：body 发完就结束的话，`EventSource` 会当成断线并触发重连。
> 这里「发 start + run 之后停住不关流」，界面就稳稳停在「训练中」，好断言。

断言 `.status` 里出现了 `run` 事件带来的现场名——这一条同时验证了
「开训前就拿到 run_id」在**界面上**真的生效，而不只是协议里发出去了。

## 七、几处动手时才知道的约束

**`_train_from_checkpoint` 里是函数内 `from ultralytics import YOLO`**，
所以测试要 `monkeypatch.setitem(sys.modules, "ultralytics", fake)`——
给它挂属性是没用的，导入发生在函数体里，那时才去查 `sys.modules`。

**`train_worker._PROTOCOL` 是模块级变量**，`emit()` 读的就是它。测试里换掉它
就能截获整条协议流，不必去包 `main()`。

**给 e2e 造 SSE 桩时，body 写完就结束等于「断线」**，`EventSource` 会重连。
这里只需要断言「训练中」那一帧，所以让响应挂着不结束最省事。

**`apps/web/tsconfig.json` 的 `include` 只含 `src/**`，不含 `e2e/`**——
e2e 里的类型错误 `npm run typecheck` 抓不到，只有跑起来才知道。

**`.status` 里除了文案还塞着 `<span class="mono">` 的 run_id**，
所以断言要用 `toContainText` 而不是 `toHaveText`（后者要求整体相等）。

## 八、遗留

- **续训改不了总轮数**（`epochs` 不在 ultralytics 的白名单里）。想多跑几十轮得开新训练。
  这条从 v1.7.0 留到现在，是 ultralytics 的语义，不是我们偷懒。
- **任务表在内存里**：服务重启后任务记录清空。但现场与检查点都在磁盘上，
  续训不受影响（这正是断点续训的价值）——按钮区因此只在「本次服务进程起过的任务」上有意义。
