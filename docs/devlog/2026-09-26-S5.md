# 2026-09-26 · S5 控制台重构

> 阶段：S5 · 产出：REST 服务层 + Vue 值班控制台（仪表盘）
> 技术设计见 [`../tech/S5-前端架构.md`](../tech/S5-前端架构.md)

---

## 起因

S4 的 Streamlit 界面已完成并归档，但评估后确认它的交互模型撑不住后续需求：
训练实时曲线需要长连接推送，而 Streamlit 是整页重跑；大文件上传的预览状态也容易丢。

决定重做界面层，并**先归档再删除**——这样即便重做失败也能回退。

## 做了什么

### 1. 归档 S4，建立干净的对照点

先修掉一个遗留缺陷再归档：`scripts/make_demo_dataset.py` 仍在用旧类别名
`["flame", "smoke"]`，且顺序与契约**相反**。后果是 VOC 路径按名字查表报「未知类别」，
YOLO 路径则把相反的数字写进 label——测试能过，但数据是错的。

修完后测试转绿，归档为两个 commit，S4 的界面代码保留在 git 历史中。

### 2. 服务层与界面解耦

`fire_sight/web/services/` → `fire_sight/services/`（用 `git mv` 保留历史）。
这一层几乎原样复用，是「路由只做校验与序列化」这条分层约束的直接收益。

### 3. REST 层

FastAPI 应用 + 两个路由（系统状态、仪表盘聚合）。实现时两个判断：

- **GPU 探测用 `nvidia-smi` 而非 torch**。首次 import torch 需数秒，会让状态接口慢到不可用。
- **空态不报错**。事件库不存在时返回全零结构——首次部署就是这个状态，它不是错误。

### 4. 前端从零建立设计体系

确定「热成像取景」方向，建立令牌、三种容器、图表规范。详见技术设计文档。

## 踩到的坑

### 归档目录有两种布局，最新一轮整个消失

仪表盘显示的 mAP 是 0.773，但最新一轮训练结果是 0.745。排查发现：

```
models/trained/<run_id>/best.pt              ← 只匹配这种
models/trained/<run_id>/<实验名>/best.pt      ← 最新一轮是这种
```

根因是用 `--dataset "D-Fire/train"` 训练，数据集名里的斜杠被带进了归档路径。
`glob("*/best.pt")` 匹配不到嵌套布局，于是最新一轮实验凭空消失，权重数也少算一个。

**第一层修法**：改用 `rglob` 并按相对路径生成 `run_id`，两种布局都认，加回归测试锁住。

**但没治根。** 顺着往上查，发现数据集名里的斜杠来自 `fs-transform`：

```python
self.raw_root = RAW_DATA_DIR / dataset        # 读
self.out_root = PROCESSED_DATA_DIR / dataset  # 写
```

同一个 `--dataset` 决定读写两侧。原始数据在 `data/raw/D-Fire/train/`，
所以只能写 `--dataset "D-Fire/train"`，斜杠于是渗进产物路径，再渗进归档路径。

产物名与输入位置被绑死在一个参数上，想换产物名就只能改 `--dataset`，
而改了 `--dataset` 原始数据又找不到——这是个死结。现新增 `--name`
（产物目录名，**默认与 `--dataset` 相同**，保持既有数据位置不变），
并在 `make_run_id` 处按 `naming` 规则清理，归档路径不再受斜杠影响：

```
fs-transform --dataset "D-Fire/train"   → processed/D-Fire/train（与输入同构）
fs-train     --dataset "D-Fire/train"   → trained/2026...-D-Fire-train-yolo11n（恒为扁平）
```

> 顺带纠正一处我自己的误判：我先按目录清单判断 `data/processed/D-Fire/` 是
> 「没有 data.yaml 的残留目录」，据此认定 `D-Fire_train` 无法复现。实际查证后发现
> 它是完整的——`data.yaml` 在 `D-Fire/train/` 下，划分计数与 `D-Fire_train`
> 逐项一致。**我只查了一层就下了结论。** 目录清单能看形状，看不出完整性。

### 类别顺序可以随便传，这是个静默的数据损坏口子

排查上面那条时顺带发现的，比上一条更危险。

`--classes` 的顺序就是 `class_id`。对 **YOLO** 输入，转换器原样透传数字 id，
所以传错顺序只是名字标错；但 **VOC / COCO** 输入是按**名字**查表的——
传 `--classes fire,smoke` 会把 `fire` 写成 id 0，而 `data.yaml` 由 `class_map`
生成、声明 `0: smoke`。

结果：**标签数据被静默调换，模型照常训练、mAP 照常好看。** 这类错误在换数据集
之前几乎不可能暴露——因为平时用的数据集恰好顺序是对的。

现改为强制要求 `smoke,fire`，不符则在建立任何目录之前拒绝执行并说明原因。
宁可拒绝执行，也不能让一个「指标正常但类别是反的」模型交付出去。

### 顺带核对了类别契约本身

怀疑上面那条已经发生过，于是直接查证：裁出单框样本看实际内容。

- `class_id = 0` → 三张全是烟柱
- `class_id = 1` → 三张全是明火

原始标签 9550 / 11814，处理后 9543 / 11807，**原样保留、未重映射**。
`data.yaml` 的 `0: smoke / 1: fire` 正确，训练数据没有问题。

出问题的是 `transform_stats.json`——它把 class 0 记成了 `fire`，名字反了。
来自一次 `--classes` 顺序颠倒的旧运行，**只影响报表，不影响标签**。
该文件已列入待清理项。

### 时间序列的缺日会伪造间隔

趋势图只返回有告警的日期，于是 X 轴上 09-01 直接跳到 09-03。
视觉上两天的间隔和一天一样宽——**坐标轴在说谎**。

改为后端恒定返回连续 `days` 项，缺日补 0。

### 但补 0 补错了地方

修完上一条，平均置信度在无告警的日子掉到 0，折线砸出深谷，
读起来像「那天模型置信度为零」。实际上那天**没有样本**，平均置信度是未定义的。

**零 ≠ 缺失**：告警次数为 0 是真的零，平均置信度为 0 是错的。
改为前端对无样本日做断点处理，不在断点间连线。

顺带把空态判断从 `daily.length > 0` 改成 `alerts.total > 0`——
连续性是序列的属性，空态是总量的属性，两者不该共用一个信号。

### 配色校验器推翻了设计原则

按「低饱和暖灰」原则把烟雾色定为 `#6E8A99`，校验器判定彩度 0.039 低于下限 0.10，
报「reads gray」——它读起来是灰色，无法承担类别标识。

不是颜色选错了，是**原则错了**：真实热成像的冷端本就是饱和青蓝，
把冷端做成低饱和灰，等于让数据色退化成了界面 chrome。
改为类别决定色相家族后，`#00A3C4` / `#D14A17` 六项全过。

### 双 Y 轴被否决

原计划把「告警次数」与「平均置信度」画在一张图上做双轴。
规范检查指出这是图表设计的头号错误：两个刻度的对齐关系是任意的，会凭空造出相关性。
改为两张共用 X 轴的小倍数图。

### 一次误判：以为风险尺定位有 bug

截图里风险尺游标停在 36%，而分数是 0.76，看着像定位错误。
用三种时间预算重拍都对不上，一度准备改代码。

开 `--force-prefers-reduced-motion` 后游标正落在 0.76 —— 是 headless 浏览器的
**虚拟时间不驱动 CSS transition**，把入场动画拍在了半路。

**代码没问题。** 教训：截图里的异常先量再改，别凭像素直觉动手。
（顺带确认了降级动效这条无障碍路径真的生效。）

## 追加：识别检测模块

仪表盘之后做的第二个模块。范围（图片 + 目录批量）早先已定，这次是实现。

### 又踩到同一类坑：命名带来的层级

批量来源列表最初只返回 `demo_fire`，**主要数据集 D-Fire 完全没出现**。
原因和之前归档嵌套同源：`--dataset "D-Fire/train"` 的产物落在
`processed/D-Fire/train/`，比 `demo_fire` 多一层，而扫描只往下看了一层。

改为以 `data.yaml` 是否存在作为完整性标志、最多认两层。用 `data.yaml`
而不是「目录存在」是因为半成品目录也会存在，只看目录会把它们列出来。

### run_id 不能从路径反推

`InferResult.weights` 一开始写的是 `path.parent.name`。扁平布局下它恰好等于
run_id，看着没问题——但嵌套布局下得到的是实验名 `train-yolo11n`，
前端拿它去对应模型列表里的条目就会对不上。

根因是信息在解析时被丢掉了：解析权重的函数只返回路径，把 run 的身份扔了。
改为返回整个 `ArchivedRun`。测试直接断言了这一点。

### SPA 深链接全是坏的

截图 `/detect` 拿到 `{"detail":"Not Found"}`。`StaticFiles(html=True)` 挂在根路径
只服务真实存在的文件，而前端用 HTML5 history 模式——**不只是识别页，
所有子页面的深链接和刷新都是白屏**。

改为先挂 `/assets`，再用兜底路由把未命中的路径交回 `index.html`，
同时对 `api/` 前缀保留 JSON 404（否则接口写错路径会收到一份 HTML）。

### 缓存是能不能用的分水岭

`InferService` 的模型是实例级懒加载的。每次请求新建实例 = 每次重新读权重：

| | 服务端耗时 |
|---|---:|
| 无缓存（首次，含加载） | 1086 ms |
| 有缓存（后续） | 16–18 ms |

改为按 `(weights, device)` 缓存实例，`conf` / `iou` 逐次传入。

### 用真实数据验证，而不是空白图

拿 D-Fire test 集里一张有标注的图跑，检出结果与真实标注**逐框对应**：

| 真实标注 | 模型检出 |
|---|---|
| 明火 (0.533, 0.687) → 中心 (682, 494) | 明火 0.87 → 中心 (681, 490) |
| 明火 (0.146, 0.675) → 中心 (187, 486) | 明火 0.56 → 中心 (187, 486) |
| 明火 (0.048, 0.675) → 中心 (61, 486) | 明火 0.34 → 中心 (48, 487) |
| 烟雾 (0.142, 0.433) → 中心 (181, 312) | 烟雾 0.31 → 中心 (174, 306) |

4 个目标全中、类别全对。这同时**独立验证了类别契约**——模型的「明火」落在
标注为 `1` 的框上，「烟雾」落在 `0` 上。

### 界面调整

- 拖放区的虚线边用 `--cinder` 几乎看不见，且取景窗已有四角框标，
  再描一圈就成两套边框语言。改为静止时安静、悬停/拖入才响应。
- 滑块是浏览器默认样式，浅色轨道在暖褐底上过亮，也看不出当前值落在哪。
  改为轨道分两段着色，已选区间用明火色。

### 未验证

headless 浏览器无法操作文件选择框，**上传 → 出结果的交互路径没有亲眼确认**。
接口侧用真实图像验证过了，但结果对比图与检测框账册的渲染需要人工点一遍。

## 追加：训练中心（回看）

第三个模块。范围是对着 `results.csv` 与现场图件做「历史训练怎么看」，
网页启动训练与实时流放在下一半单独做。

### 一条曲线把整张图压平了

第一版把六条损失画在一张图上。渲染出来一看：`val/cls_loss` 前三轮从 28.8 冲到
**87.2** 再回落到 1.55，而其余五条全程在 1.1–2.2。58 倍的差距摆在一根线性轴上，
其余五条全被压成贴底的直线，那张图等于没画。

先确认这是不是渲染问题——查了原始 CSV，是真实数据。分类损失在模型还没学会区分
两类时剧烈震荡，属于正常现象，不该被藏掉。

处理方式：**每种损失一张小倍数图，各自自适应量程**。cls 那张照实显示震荡，
box 与 dfl 两张不再受牵连。没有改用对数轴——变换坐标能把六条塞回一张图，
但那是对读者耍花招，不如分成三张各说各的事。

顺带发现：分成小倍数后每张图内只剩「训练 / 验证」两条，用实线虚线区分就够了，
一个颜色都嫌多，因此损失图根本不需要类别色板。

### 训练曲线不能借用类别色

青（#00A3C4）与橙（#D14A17）已经表示烟雾与明火。拿它们表示训练/验证或损失类型，
同一个颜色在同一套界面里就有了两种含义。训练曲线因此单独配色。

选色过程被校验器反复打回，值得记下来：
- 蓝 + 紫：deutan 下 ΔE **1.4**，几乎完全同色
- 琥珀 + 浅青：明度 0.806 / 0.865，**超出暗色模式 0.48–0.67 的明度带**；浅青彩度
  0.06 也低于下限 0.10，会被读成灰色
- 琥珀 + 绿：protan 下 ΔE 4.0

最终 `#4C8FE0 / #BE8219 / #B85FA8 / #4FA050` 全过：最差相邻对 deutan ΔE 13.0、
常视觉 21.6。**顺序不能重排**——把绿与琥珀排到相邻就会掉回 ΔE 4。

### run_id 含斜杠，不能走路径参数

`run_id` 形如 `20260926-190635-D-Fire/train-yolo11n`，用 `{run_id}` 路径参数会被
路由切碎。四个接口一律改用查询参数传 `run_id`，并只接受已发现的 run。

图件接口额外限制：`name` 只允许现场目录下的顶层文件名。带路径分隔符一律 400，
非图片后缀一律 404——否则这个接口就成了任意文件读取。

### 顺带看清了现有数据的状态

训练记录账册把现场全列出来了，暴露出一件事：三个 `D-Fire_train` 训练分别是
**50 / 10 / 3 轮**，后两个是中途中断的实验，而且它们用的数据集已经被删除。
它们没有归档，因此指标为「—」，但曲线还在现场，仍可查看。

## 追加：训练中心（实时）

### 为什么训练跑在子进程里

训练崩了不该把 API 一起带走，所以用子进程：父进程起 `train_worker`，读它的管道
转 SSE，并在进程退出时释放 GPU 锁。

难点在协议流与日志流会串。ultralytics 自己往 stdout 打大量日志，混进来就没法
按行解析。解法是 worker 导入的第一件事就把 `sys.stdout` 改道到 stderr——
**改道必须发生在 import ultralytics 之前**，否则它的日志 handler 已经绑定了
原来的 stdout。此后协议写在真 stdout，日志走 stderr，两条流都干净可用。

归档逻辑没有另起一套：worker 调的就是 `train_yolo`，只是给它加了一个可选的
逐轮回调。网页启动的训练与命令行启动的训练因此走完全相同的归档路径。

### 训练损失静默消失

第一次跑通时，SSE 里只有 `val_*` 没有 `train_*`。查下来：

`trainer.loss_items` 返回的是 **dict**（`{'box_loss': tensor, 'cls_loss': tensor, ...}`），
不是序列。而代码写的是 `[float(x) for x in loss_items]`——迭代 dict 拿到的是**键名**
（字符串），`float("box_loss")` 抛异常，被我自己的容错 `except` 吞掉，
于是训练损失无声无息地没了。

**是测试的疏漏让它漏过去的**：我从没断言过 train 损失必须出现。已补三个用例
（dict 形态、序列形态、脏数据容错）。

### 指标慢一轮、还多出一轮

用 `on_train_epoch_end` 时第一轮指标全是 0——那一刻本轮验证还没跑。
改用 `on_fit_epoch_end`：ultralytics 写 `results.csv` 正是在那一刻，两者严格对齐。
实测逐值核对，回调与 CSV 行完全相同。

但新的回调在训练结束后的收尾验证时**又触发一次**，实时曲线上多出一个 `epochs+1`
的假点。加了一道守卫：`epoch > epochs` 直接丢弃。

### 中途验证用的是什么配置

`demo_fire` + `fraction=0.4` + `epochs=3` + `imgsz=320`，二十来秒跑完。
逐值核对 SSE 事件与 `results.csv`，完全一致。GPU 锁在进程退出后正确释放
（`/api/system/status` 的 `gpu_job.busy` 回到 false）。

一个反直觉的观察：三轮的验证指标**完全相同**。查 CSV 确认属实——
`fraction=0.4` 只取了两张训练图、验证集一张，模型几乎没变。
不是 bug，是小数据集的固有现象。

### 清理

验证期间起了 4 次训练，产生了 4 个 demo 归档（mAP 0.09–0.14 的垃圾值），
把真实的 D-Fire 模型从"当前模型"挤了下去。已全部删除，归档恢复干净。

**这正是自动化验证的价值边界**：验证跑通了链路，但副作用会污染真实状态。
以后这类验证应当在隔离目录下做，而不是直接写进 `models/trained/`。
