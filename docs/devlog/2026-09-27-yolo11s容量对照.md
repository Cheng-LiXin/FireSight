## 一、设计：只差模型

用户 17:16 自己跑过一次 `yolo11n` / 30 轮 / imgsz=512 / batch=40 / fraction=1.0 / seed=42，
已归档（mAP50 0.7432）。**所以 n 那一侧不必重跑**，直接拿它当对照，只换模型：

| | n 基线（已有归档） | s 本次 |
|---|---|---|
| model | yolo11n | **yolo11s** |
| batch | 40 | **34** ← 显存守卫压下来的 |
| epochs / imgsz / fraction / seed / workers / cache / device | 30 / 512 / 1.0 / 42 / 4 / false / 0 | 全同 |

`batch` 是唯一的不同，而且**不是我选的**：守卫在 imgsz=512 给 yolo11s 的上限是 34
（n 是 63），提交 40 直接 400。这正是 v1.5.1 那套实测因子的用途——旧守卫会放行。

这个混杂的方向是**对 s 不利**（更小的 batch），所以「s 更好」这个结论不会因此打折。

两边都跑满 30 轮、学习率轨迹相同，所以逐轮**配对比较**成立（P0-1 的方法）。

## 三、和 P0-1（分辨率）并排看

| 杠杆 | 配对差 mAP50 | 成本倍数 | 结论 |
|---|---|---|---|
| 训练分辨率 640 → 960 | **−0.0090**（t=−1.14，不可区分） | 2.21× | 负收益，**停手** |
| 模型容量 n → s | **+0.0195**（后 15 轮 16/16） | 1.65× | 正收益，**继续** |

所以 P0-1 的建议（转模型容量）得到了验证：**同一个「加算力」的动作，花在容量上有效，
花在分辨率上无效**——而且容量还更便宜。这符合任务本身的性质：D-Fire 的 fire 目标
中位框只占画面 7.1%（P0-1 的发现），瓶颈在**表征能力**而不是像素数。

## 四、但别把结论说过头：它不是「换 s 就升级」

翻归档明细会发现一件必须说清的事：

| mAP50 | 归档 | 模型 / 轮数 / imgsz / batch |
|---|---|---|
| **0.7675** | `20260927-112418-D-Fire-train-yolo11n` | yolo11n / **50 轮 / 640px** / b40 |
| 0.7585 | `20260927-194539-D-Fire-train-yolo11s` | yolo11s / 30 轮 / 512px / b34 |
| 0.7446 | `20260926-190635-D-Fire/train-yolo11n` | yolo11n / 50 轮 / 480px / b72 |
| 0.7432 | `20260927-171606-D-Fire-train-yolo11n` | yolo11n / 30 轮 / 512px / b40 |

**这次实验证明的是「容量这个杠杆是正的」，不是「s@30ep/512 比现役模型好」。**
现役最好那份是 **n / 50 轮 / 640px = 0.7675**，s 这次只到 0.7585，仍低 0.009。

要让 s 在**同等预算**下比它，就得给 s 同样的 50 轮 / 640px：
每轮约 108.3 × (640/512)² ≈ 169 s → 50 轮约 **2.4 小时**。
那才是能给出「要不要换」答案的实验。

## 五、顺带实测到守卫的一个真问题

训练期间显存 **7356–7470 MiB / 8188**，桌面空闲时占 1663 MiB，所以训练自身峰值约
**5700 MiB**。而 `vram.py` 对同一配置（s / batch 34 / 512）的预测是 **4833 MiB**，
差约 870 MiB。

原因在**标定口径**：当初量因子用的是 `val=False` + 1 轮，所以不含

- **每轮验证**（1722 张，且 `rect=True` 可能组出大 batch）
- **mosaic 增强**（前 20 轮开启）

后果是：守卫文档里那句「各档余量约 1.7 倍」**在真实训练里不成立**——达到守卫上限时
实际已占卡的 **90%**。更准确的说法是：

> 标定点对应的真实峰值约 5700 MiB，而卡上有约 1.6 GB 不归 CUDA 用（桌面）。
> 守卫按**总显存** 8188 算预算，所以桌面占用涨到 3 GB 时，同一配置就会 OOM。

**没有改。** 修法是按**可用显存**（`total − used`）算预算，代价是上限收紧：
s@512 从 34 降到约 27、n 从 63 降到约 52。这是「安全 vs 能开的批量」的取舍，
应由使用者决定。已记进 HANDOFF 的下一步。

## 八、补记：同预算跑到 50 轮（决定性结果）

召回率 0.702 → 0.720 尤其值得记：它是这个产品一直的弱项。

### 代价（顺带修正上面那张表里的一个数）

`results.csv` 的 `time` 列是**当前进程**的累计秒数，续训会把它清零重算，
所以脚本按它算出的「s 26.6 分钟 / 50 轮（31.9s 每轮）」是假的。真实成本要两段相加：

| | n | s | 倍数 |
|---|---|---|---|
| 每轮 | 97.7 s | ≈168 s（前 40 轮实测 170.4s；后 9 轮 26.6 分钟） | **1.72×** |
| 50 轮总时长 | 81.4 分钟 | ≈140 分钟 | 1.72× |
| 推理（imgsz=640） | 1.6 ms | 3.2 ms | 2.0× |

推理那 2× 对本产品仍不构成约束（连前后处理约 5 ms/帧 ≈ 200 fps，视频源 25–30 fps）。

### 结论

**换 s。** 它在每一项指标上都更好，代价是训练 1.72×、推理 2×（而推理不紧张），
而且现在是归档里最好的一份（0.7882 > 0.7675）。「容量是正收益的杠杆」
从「证明方向」升级成了「给出可换的具体模型」。

> 一个副产品：这是**第一次「最新归档 = 最好归档」**。之前几次（P0-1 的探针、
> 17:16 那次 30 轮实验）都是最新那个更差，正是 v1.6.0「设为当前」要解决的问题。
